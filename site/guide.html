.intel_syntax noprefix
.include "stubbi/math/0.4.0/x86_64-linux/src/min.s"

.section .text
.global _start
_start:
    mov edi, 12
    mov esi, 37
    call asm_u64_min
    cmp rax, 12
    jne .Lfailure
    mov eax, 1
    mov edi, 1
    lea rsi, [rip + message]
    mov edx, message_end - message
    syscall
    mov eax, 60
    xor edi, edi
    syscall
.Lfailure:
    mov eax, 60
    mov edi, 1
    syscall

.section .rodata
message: .ascii "min(12, 37) = 12\n"
message_end:

THE PACKAGE MODEL

The target is part of the package.

Check the target, calling interface, and build instructions before you reuse a package. Some requirements are stated in its documentation.

Machine requirements

The instruction set, required CPU features, operating system, and object format determine where the code can run.

Calling interface

The application binary interface (ABI) defines calls and data layout. Read the package's symbol names, memory ownership, and register use.

Build record

Declared tools, pinned inputs, and recorded outputs give you something concrete to reproduce and review.

Read the package design ↗

RELEASE EVIDENCE

Show the evidence.

Package records show metadata checks, artifact checks, and checks that were not run. Read each result's version, target, scope, and assumptions.

Read the security model ↗

Each release lists its current checks. Hosted proof and analysis services are planned.

Integrity

Size and SHA-256 checks compare a file with its release record. A matching digest does not establish publisher identity or safety.

Provenance

Connects an artifact to its source, build process, and publisher identity within a stated policy.

Scanning

Records what a named tool inspected, the tool version, and its findings.

Testing

Records the inputs, target, environment, and observed results of specific tests.

Formal proofs

Establish stated mathematical properties within a model and explicit assumptions.

Agent review

Provides advisory analysis. It does not replace an accountable review or a release gate.

WHY Asm

Make the useful work reusable.

Software should serve people well and use resources with care. Assembly gives builders direct control over instructions and machine features.

We expect AI to make assembly cheaper to create and maintain. More generated code makes dependable reuse and inspectable evidence more important.

Asm brings assembly projects, packages, targets, and release evidence into a shared workflow. People decide what to build, what to use, and what to trust.

Assembly must earn its place through correct behavior, useful results, and measured total cost.

Read the project motivation ↗

A measured example

An asmwc experiment measured default counting on a 128 MiB text file. On Apple M3 with macOS 15.6.1, median time was 15.234 ms for optimized assembly and 68.468 ms for native Rust. Each implementation had 24 samples with a warm file cache. The comparison includes algorithm, I/O, and startup differences. Asm checked the published records; we have not reproduced the experiment.

BUILT IN THE OPEN

What comes next.

Asm 0.7.0 supports local projects, standalone Linux cross builds, and signed V2 dependency graphs for configured registries. Official hosted V2 activation and hosted verification remain gated.

Full roadmap ↗
  • NOW

    CLI foundation

    A native assembly executable, local project commands, and a format for package records.

  • NOW

    Dependency graphs

    V1 exact selections; signed V2 ranges, optional dependencies, features, and complete graph locks. Source files and target-specific artifacts remain checked.

  • PLANNED

    Hosted registry operations

    Official V2 activation, self-service enrollment, ownership transfer, and account recovery.

  • RESEARCH

    Deeper assurance

    Clients for more hosts, isolated analysis, and scoped proof checks for supported routines.
