# V2 Website Implementation Plan

**Goal:** Find an exact V2 release, fetch its bytes, and inspect its attributed download observations through the website.

**Architecture:** Add an explicit V2 static build mode to the existing site builder. Read the operator-selected public mirror inventory and private observation ledger. Reuse the existing page chrome, styles, search, and controls. Assembly continues to own publication, selection, lifecycle checks, and native use; no public application backend is added.

**Spec:** The [V2 website contract](../../specs/registry-v2.md#static-website-projection) extends the existing distribution and observation contracts.

## Constraints and trade-offs

- Keep default V1 builds and released CLI behavior intact.
- Do not invent V1 records, publication dates, source-host routes, evidence, or missing counts.
- Keep immutable registry, package, and release identities in public JSON and statistics bindings.
- Treat the local inventory as trusted operator input, not client signature or rollback verification.
- Native fetch commands require independently provisioned trust and current TUF/lifecycle checks.
- Keep raw download links disabled unless the builder checks their exact artifact bytes.
- Static pages can lag distribution. Expose their distribution revision and observation cutoff.
- Statistics refresh reads metadata and the ledger, without downloading artifacts or querying the application database.
- Use no new service, dependency, tracker, or per-download database write.
- No deployment, production trust, CDN activation, or source-host integration is authorized by this change.

This serves consumers who need compatible bytes and inspectable evidence.
It follows resource care, dependable reuse, control, and evidence principles.
The trade-off is bounded static discovery and rebuild delay instead of another running service.
