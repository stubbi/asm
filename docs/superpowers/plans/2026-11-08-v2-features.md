# V2 optional dependencies and features

The user outcome is an exact, repeatable dependency selection with optional packages omitted until requested.
This follows resource care, explicit control, and inspectable evidence in the brand foundation.
Application logic remains assembly. The existing bounded solver and signed metadata transport remain in use.

## Contract

- Keep mandatory string declarations compatible.
- Permit inline `version`, `optional`, `default-features`, and `features` dependency fields.
- Permit sorted local feature groups, `dep:owner/name`, and `owner/name/feature` members.
- Validate all declarations, including inactive declarations, before changing files.
- Reject unknown local references, duplicate members, local cycles, and capacity overflow.
- Unite active child requests. A disabled default on one edge cannot subtract another edge's request.
- Apply no version constraint or feature request from a dormant edge.
- Support consistent package cycles with finite monotone feature propagation.
- Backtrack when a candidate lacks a requested child feature.
- Fetch metadata only for names reached by an active solver branch.
- Keep one explicit target and registry, 256 reached candidates, 64 declarations per list, and a global search budget.
- Expose `--features A,B` and `--no-default-features` on explicit resolve only.
- Write complete version-four graph locks with selection, enabled features, active edges, and immutable node bindings.
- Retain verified envelope bytes in a digest-addressed local metadata cache for offline build checks.
- Preserve version-three mandatory graph compatibility. Refuse complex declarations in version-three locks.
- Features affect graph selection. Source imports remain explicit; no compiler conditional language is added.

## Acceptance conditions

1. Native publication produces canonical declarations from an exact committed source tree.
2. Private checks and signed distribution compare all source declarations without changing original publication bytes.
3. Native resolve, sync, local build, and run cover default and explicit selections on supported hosts.
4. Complete locks reject omitted edges, forged feature state, missing metadata, changed bindings, and stale root manifests.
5. Conflict, unavailable metadata, corrupt source, unsupported targets, existing destinations, and resource limits preserve existing files.
6. Independent exhaustive graph cases agree with both native solver implementations.
7. Required CLI, verifier, registry, publisher, infrastructure, site, and release gates pass for the released bytes.
8. Publish through the protected repository flow. Download and verify the resulting release and public site.

## Trade-offs and release limits

Version-four locks retain selection and active graph facts. Exact envelope files retain dormant declarations without expanding each lock.
This adds one small cache object per selected package. It avoids network access during local build checks.
The initial fixed bounds constrain capacity; they do not establish global scale or comparative cost savings.
Official hosted V2 activation still requires independent trust provisioning, signing custody, storage identities, and deployment qualification.
Fixture roots and successful local tests cannot satisfy those production inputs.
